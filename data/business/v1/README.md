# 模拟业务规格

这些是假想售后业务的模拟样例，不代表真实商家的政策或法律要求。数据包含初始订单、历史操作和独立的期望结果。

## 时间、金额与文件

- `spec.json` 固定业务时间为 **2026-09-17 12:00:00 +08:00**。资格计算和样例运行使用该时间，不使用电脑当天时间；将来的运行日志仍记录实际执行时间。
- 币种仅为 CNY；所有金额使用整数“分”，100 分 = 1 元。例如 12900 表示 129 元。金额不接受小数或布尔值，订单实付大于 0。
- `orders.json` 是 4 个订单的初始快照；实付包含本样例的全部可退金额，不另建运费、部分退款或多商品拆单规则。
- `operations.json` 是初始已成功操作及其确认快照。ORD-1003 已有 9900 分退款，必须连同历史确认、操作和订单状态一起导入，不能只改订单上的累计金额。
- `scenarios.json` 是 5 个独立运行的例子及手工期望，覆盖 4 类任务。每个例子从同一份初始数据独立重置，不能顺序修改并共享同一业务库；两个使用 ORD-1001 的例子也不共享写入。

## 模拟规则 v1

规则版本 `mock-policy-v1`，有效区间为 `[2026-09-01T00:00:00+08:00, 2026-10-01T00:00:00+08:00)`。执行写操作时检查适用版本和业务时间；到期规则不能继续授权新操作。下面的规则 ID 用于对照规格，不是检索文档引用。

| 规则 | 条件 | 结果与边界 |
|---|---|---|
| R-REFUND-01 | `general_goods`；平台已核实到货损坏；已收货，距收货不超过 7×24 小时 | 经确认后退全部实付金额；恰好 7 天仍符合；超出则转人工。每订单最多一笔全额退款，改操作键不能再次退；退款金额必须等于实付，已退款时查询原结果 |
| R-DELAY-01 | `general_goods`；实际送达比承诺送达晚至少 24 小时 | 经确认后发 500 分补偿券，恰好 24 小时符合；每订单最多一张，可与退款组合。该样例的补偿判定不依赖损坏，也不继承退款的 7 天期限 |
| R-HANDOFF-01 | 不支持的品类、退款超期、损坏尚未核实，或澄清一次后仍无法定位订单 | 经确认后创建人工工单，记录原因和已有证据；不承诺已经退款或补偿 |

缺订单号先澄清，不按产品描述猜测。`digital_goods` 统一转人工，数字内容发放时间沿用 `delivered_at` 字段。5 个例子都能在初始请求或一次澄清后定位订单；`order_unresolved` 表示澄清后仍无法定位订单的空订单转人工原因。

三种写操作都必须走提案、确认、执行。组合动作逐项确认，可以在一次交互中批准两个明确列出的提案；修改订单、金额或动作参数必须重新确认。拒绝后不执行相应动作；表中成功期望假设操作者批准所列动作。

仅把成功提交算作业务写入。退款与补偿是各自的业务事务，组合任务可能部分完成；重试或恢复应保留已成功动作并核对账本，不把整组当作一个不可分割事务。转人工也按同一问题去重；提案和执行上下文结构见[契约说明](../../../docs/contracts.md)。

## 四类任务与可核对期望

| 类型 / 示例 ID | 初始状态与需要做的决定 | 本次预期新增业务写入 | 最终累计金额（分） |
|---|---|---|---|
| `policy_refund` / `refund-damaged` | ORD-1001 已核实损坏且在期限内，查询规则并提出退款 | 1 笔退款 | 退款 12900，券 0 |
| `refund_and_coupon` / `refund-with-delay-coupon` | ORD-1002 损坏且晚到 26 小时，识别两项可兼容措施 | 1 笔退款、1 张券 | 退款 25900，券 500 |
| `reconcile_operation` / `check-uncertain-refund` | 请求方不知道退款结果，实际账本已成功；按已知原操作键核对 | 0；不得再退款 | 退款仍为 9900，券 0 |
| `clarify_or_handoff` / `clarify-order-before-refund` | 首次未提供订单，先请求补充，取得 ORD-1001 后再提案 | 1 笔退款；澄清前 0 | 退款 12900，券 0 |
| `clarify_or_handoff` / `handoff-digital-goods` | ORD-1004 不支持自动退款，选择转人工并说明原因 | 1 个人工工单 | 退款 0，券 0 |

不确定结果样例仅预置“已提交但请求方未知”的业务状态，用于按原操作键核对；没有注入网络故障，也不能证明故障恢复能力。历史操作原键由运行时已有记录提供，不让模型凭空猜测。

## 数据使用约定

- 运行时将 `owner_id` 作为模拟操作者身份注入可信上下文；不能将前端提交的身份直接作为授权依据。仅向模型展示用户当前消息、已知订单/操作键及实际工具结果。
- `expected` 是手工期望，`clarification_reply` 是用户模拟器稍后才能提供的回复，初始状态不得把这两部分灌入模型。每项 `new_actions` 都需要对应确认；其列表不是要求模型遵守的工具顺序。
- 历史确认与操作仅用于初始化隔离演示数据，不提供业务执行器的免确认分支。追加操作仍须通过业务服务，不能依靠 JSON 字段自授权。
- 这些例子是模拟业务样例，不能拿其通过率充当业务成功率、训练结果或固定 test 结果。
- `scripts/check_business_data.py` 只核对金额类型、引用、初始退款账本和手工期望的一致性，输出预期结果预览，不执行资格规则。

从项目目录运行：

```powershell
uv run --no-sync --cache-dir .uv-cache python scripts/check_business_data.py
```

入口使用应用配置的 `business_data_dir`，读取不会创建数据库或修改订单。
